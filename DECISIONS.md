# Журнал решений

Каждая запись фиксирует принятое решение, причину и последствия. Решения,
меняющие научную постановку, принимает владелец проекта; Claude Code
фиксирует здесь инженерные решения и выносит методологические на утверждение.

## Этап 0 — Каркас

### D-001. Ревизия StatsBomb Open Data зафиксирована commit SHA

**Дата:** 2026-08-23
**Решение:** источник привязан к `hudl/open-data@b0bc9f22dd77c206ddedc1d742893b3bbe64baec`,
SHA хранится в `configs/data.yaml`, все URL строятся от него.
**Причина:** StatsBomb регулярно обновляет Open Data. Загрузка с ветки `master`
сделала бы результаты невоспроизводимыми (спецификация, раздел 5.4).
**Последствия:** обновление данных — явное действие: сменить SHA, перезапустить
аудит и пересобрать манифест. Кеш разделён по SHA, поэтому ревизии не смешиваются.

### D-002. Загрузка избирательная, репозиторий источника не клонируется

**Дата:** 2026-08-23
**Решение:** метаданные (`competitions.json` и все файлы матчей, 7.2 МБ)
скачиваются целиком; события и файлы 360 — только для явно заданных матчей.
**Причина:** в зафиксированной ревизии источник содержит 12.8 ГБ событий и
3.2 ГБ файлов 360. Полная загрузка не нужна ни для аудита, ни для эксперимента.
**Последствия:** в `download_data.py` есть `--dry-run` и предохранитель `--max-gb`
(по умолчанию 5 ГБ); объём известен заранее из git-tree.

### D-003. Инвентаризация источника через git-tree, а не перебором файлов

**Дата:** 2026-08-23
**Решение:** один запрос GitHub API `git/trees/<sha>?recursive=1` даёт полный
список файлов ревизии с размерами; ответ кешируется на диск.
**Причина:** даёт точную перепись (какие матчи имеют события, какие — файлы 360)
и оценку объёма загрузки без единого скачивания. Альтернатива — перебор с
`HEAD`-запросами — упёрлась бы в лимит GitHub API (60 запросов в час без токена).
**Последствия:** проект тратит ровно один запрос к API; `GITHUB_TOKEN`
поддерживается, но не обязателен. Если GitHub вернёт усечённое дерево,
`fetch_source_inventory` падает с явной ошибкой, а не работает по неполным данным.

### D-004. Неизвестный исход удара — исключение, а не молчаливый ноль

**Дата:** 2026-08-23
**Решение:** `map_shot_outcome` поднимает `UnknownShotOutcomeError` для `None`
и для значений вне `KNOWN_SHOT_OUTCOMES`.
**Причина:** прямое требование спецификации (раздел 8.2). Молчаливое приведение
к нулю занизило бы долю голов и исказило бы калибровку.
**Последствия:** изменение схемы StatsBomb приведёт к падению пайплайна с
понятной ошибкой, а не к тихо испорченным данным. Это правило немедленно
окупилось — см. D-011.

### D-005. Проверка запрещённых колонок ловит и производные имена

**Дата:** 2026-08-23
**Решение:** `assert_no_forbidden_columns` проверяет точные совпадения,
one-hot производные (`shot_outcome_Goal`) и префиксы `ColumnTransformer`
(`num__statsbomb_xg`).
**Причина:** после `ColumnTransformer` имена колонок меняются, и проверка только
по точному совпадению пропустила бы утечку (спецификация, раздел 9.4).
**Последствия:** возможны ложные срабатывания на легитимных именах, начинающихся
с запрещённого префикса; такие случаи покрыты тестом и решаются переименованием.

### D-006. Модуль `audit.py` добавлен сверх структуры из спецификации

**Дата:** 2026-08-23
**Решение:** логика аудита вынесена в `src/xg_context/audit.py`, а не размещена
в `data.py` или целиком в скрипте.
**Причина:** раздел 14 спецификации перечисляет модули целевого проекта, но не
запрещает добавления. Аудит — самостоятельная и тестируемая область: смешивание
его с загрузкой сделало бы `data.py` перегруженным, а размещение в скрипте
нарушило бы правило «логика в `src/`, скрипты тонкие» (раздел 14).
**Последствия:** отклонение от буквы структуры зафиксировано здесь явно.

### D-007. Часть тестов из структуры спецификации отложена

**Дата:** 2026-08-23
**Решение:** на этапах 0–1 созданы `test_target_mapping.py`, `test_geometry.py`,
`test_no_leakage.py`, `test_data_source.py`, `test_audit.py` — 117 тестов.
Перечисленные в спецификации `test_context_features.py` и `test_splitting.py`
появятся вместе с кодом, который они проверяют (этапы 2 и 3).
**Причина:** тестовые файлы без тестируемого кода были бы пустой формальностью.
**Последствия:** отсутствие этих файлов — не пропуск, а плановый долг;
он отражён в `PROGRESS.md`.

## Этап 1 — Аудит данных

### D-008. Доступность `freeze_frame` оценивается по стратифицированной выборке

**Дата:** 2026-08-23
**Решение:** аудит разбирает по 3 матча на каждый competition-season
(детерминированная выборка, seed 42) — 181 матч и 4996 ударов, — а не все
3961 матч источника.
**Причина:** полный разбор потребовал бы скачать 12.8 ГБ. Стратификация по
сезонам гарантирует, что в выборку попадут все эпохи, турниры и схемы данных.
**Последствия:** доли доступности — оценка с выборочной погрешностью, что явно
оговорено в отчёте. Числа матчей, файлов и объёмов при этом точны, потому что
берутся из git-tree, а не из выборки. Фактическая доля пересчитывается на
этапе 2 по полной выборке.

### D-009. Рекомендация по выборке формируется в два шага явными критериями

**Дата:** 2026-08-23
**Решение:** `rank_candidates` отбирает competition-season по четырём порогам
качества (доля контекста ≥ 95%, доля вратаря ≥ 90%, ≥ 50 матчей,
≥ 1500 ударов), затем `build_homogeneous_blocks` группирует прошедших в
однородные блоки «пол + сезон», и `select_recommended` берёт самый крупный
блок, помещающийся в бюджет 5 ГБ.
**Причина:** первая версия критериев рекомендовала «всё, что прошло фильтры» —
14 сезонов и 8.3 ГБ, смешивая мужской и женский футбол и эпохи 2003–2024.
Это противоречит разделу 6 спецификации: «нельзя бездумно смешивать разные
эпохи, неполные соревнования и несовместимые схемы». Пороги в коде можно
обсудить и изменить; рекомендация, дописанная вручную поверх таблиц, была бы
невоспроизводима.
**Последствия:** `reports/data_audit.md` — генерируемый файл; править нужно код
и перезапускать `scripts/audit_data.py`, а не текст отчёта.

### D-010. Основной источник защитного контекста — `shot.freeze_frame`

**Дата:** 2026-08-23
**Решение:** проект строится на `shot.freeze_frame` внутри событий удара;
отдельные файлы StatsBomb 360 не используются.
**Причина:** подтверждено проверкой в аудите. Решающий аргумент — покрытие, а не
содержание кадра: файлы 360 существуют лишь для 426 матчей источника из 4235,
и **ни один из 1517 матчей рекомендуемой выборки их не имеет**. При этом в
проверенных матчах 360 покрывает почти те же удары (55 против 53 из 55) и
добавляет около одного игрока в кадр, стоя при этом 8.4 МБ против примерно
3 МБ у файла событий. Опора на 360 означала бы смену выборки на вчетверо
меньшую ради минимального прироста информации.
**Статус:** требует подтверждения владельцем проекта (O-002).
**Последствия:** пайплайн не зависит от наличия 360; это прямая мера против
«data-engineering rabbit hole» из раздела 22 спецификации.

### D-011. Имена исходов удара сверены с данными, а не взяты из памяти

**Дата:** 2026-08-23
**Решение:** `KNOWN_SHOT_OUTCOMES` содержит `"Saved Off Target"` и
`"Saved to Post"` (со строчной `to`).
**Причина:** первая версия конфигурации использовала правдоподобные, но
неверные `"Saved Off T"` и `"Saved To Post"`. Аудит на реальных данных выявил
31 удар с «неизвестным» исходом — именно потому, что `map_shot_outcome`
падает на неизвестных значениях вместо молчаливого нуля (D-004). Без этого
правила 31 сейв был бы тихо помечен как не-гол, и ошибка осталась бы незамеченной.
**Последствия:** добавлен регрессионный тест
`test_plausible_but_wrong_spellings_are_rejected`. Число пригодных ударов в
выборке аудита выросло с 4874 до 4905.

### D-012. Ключевой результат аудита: защитный контекст доступен практически везде

**Дата:** 2026-08-23
**Решение:** проект исходит из того, что `context_eligible_shots` практически
совпадает с `all_eligible_shots`.
**Причина:** в выборке аудита `shot.freeze_frame` есть у **100%** пригодных
непенальтистских ударов (4905 из 4905), координаты соперников — тоже у 100%,
вратарь распознан у 99.86%. Доля с контекстом равна 1.000 во всех 80
competition-season без исключения.
**Последствия:** главный риск спецификации («неполный freeze-frame», раздел 22)
на этих данных не реализовался. Разделение на две выборки из раздела 8.4
сохраняется как контракт кода, но фактически они совпадут, и приписать разницу
метрик отбору строк будет нельзя. Это упрощает интерпретацию центрального
ablation-эксперимента: сравнение идёт на одних и тех же строках без потери объёма.

## Решения владельца проекта (утверждены 2026-08-23)

Открытые вопросы O-001 … O-005 закрыты. Принято:

1. **Выборка** — La Liga (11/27), Premier League (2/27), Serie A (12/27),
   Ligue 1 (7/27) сезона 2015/2016. Разовая загрузка 4.57 ГБ разрешена.
2. **Источник контекста** — только `shot.freeze_frame`; StatsBomb 360 не загружается.
3. **Популяция** — четыре лиги считаются одной целевой популяцией: ведущие

   leave-one-league-out допустим только как необязательная проверка после
   завершения основного исследования.

## Этап 2 — Датасет и признаки

### D-011a. Разреженные булевы поля проверены на данных, а не приняты на веру

**Дата:** 2026-08-23
**Решение:** отсутствие полей `under_pressure`, `one_on_one`, `open_goal`,
`first_time` трактуется как `False`.
**Причина:** спецификация (раздел 9.5) запрещает автоматически превращать
отсутствующий boolean в `False`, «если схема этого не гарантирует». Поэтому
`build_dataset.py` собирает статистику встреченных значений: все восемь
разреженных полей приняли **только** значение `true` на 37 888 ударах,
значение `false` не встретилось ни разу. Это и есть требуемая гарантия.
**Последствия:** проверка воспроизводится при каждом запуске и попадает в
`reports/data_audit.md`; смена схемы StatsBomb будет замечена.

### D-012a. Вратарь отделён от полевых соперников

**Дата:** 2026-08-23
**Решение:** соперник с `position.name == "Goalkeeper"` исключается из счётчиков
плотности обороны и описывается собственной группой признаков.
**Причина:** вратарь влияет на исход принципиально иначе, чем полевой защитник.
Смешав его с остальными, мы бы одновременно испортили и счётчики плотности
(вратарь почти всегда «в конусе»), и вратарскую геометрию.
**Последствия:** `n_opponents_visible` считает только полевых игроков;
отсутствие вратаря в кадре даёт `NaN` во всех вратарских признаках и `0`
в флаге `has_goalkeeper`.

### D-013. `n_opponents_visible` включён в модель как признак

**Дата:** 2026-08-23
**Решение:** число видимых в кадре соперников — полноценный признак, а не
только диагностика.
**Причина:** `shot.freeze_frame` показывает в среднем 7.5 соперника вместо
десяти полевых: кадр ограничен полем зрения камеры. Все остальные счётчики
поэтому смещены вниз неизвестным образом. Признак «сколько игроков вообще
видно» даёт модели возможность откалибровать это смещение.
**Последствия:** ограничение явно оговорено в отчётах; счётчики защитников
нельзя интерпретировать как «сколько соперников было на поле».

### D-014. Пропуски вратарской геометрии: импутация плюс явный флаг

**Дата:** 2026-08-23
**Решение:** в `Pipeline` числовые пропуски заполняются медианой train,
но в наборе признаков остаётся `has_goalkeeper`.
**Причина:** координаты вратаря выдумывать нельзя (раздел 9.5), а модели
нужен числовой вход. Медиана плюс флаг позволяют модели отличить «вратарь
на своём месте» от «вратаря не видно», не изобретая координат.
**Последствия:** затрагивает 0.085% ударов, поэтому влияние на результат
пренебрежимо, но контракт соблюдён.

## Этапы 3–5 — Модели, ablation и выводы

### D-015. Ablation разделён на четыре уровня, а не на два

**Дата:** 2026-08-23
**Решение:** уровни L1 геометрия → L2 характеристики удара → L3 готовые флаги
StatsBomb → L4 собственный пространственный контекст.
**Причина:** прямое требование задания. Если бы `under_pressure`, `one_on_one`
и `open_goal` попали в один уровень с нашей геометрией защитников, прирост
от **самостоятельного** расчёта был бы завышен за счёт разметки провайдера.
Разделение оказалось содержательным: флаги StatsBomb значимого прироста не
дали, а собственный контекст дал.
**Последствия:** тест `test_ablation_levels_are_strictly_nested` проверяет, что
каждый уровень строго добавляет признаки к предыдущему.

### D-016. Разбиение — жадное балансирующее назначение матчей

**Дата:** 2026-08-23
**Решение:** внутри каждой лиги матчи сортируются по числу голов и жадно
раздаются той части выборки, у которой наибольший относительный дефицит ударов.
**Причина:** требование владельца — сопоставимые доли лиг **и** сопоставимая
доля голов. `GroupShuffleSplit` даёт только первое приблизительно и не
контролирует target. Полученный результат: доли лиг расходятся не более чем
на 0.3 п.п., доли голов — на 0.07 п.п.
**Последствия:** разбиение детерминировано и не зависит от порядка строк
(проверяется тестом); тестовые `shot_id` зафиксированы в `split.json`.

### D-017. Градиентный бустинг — `HistGradientBoostingClassifier`

**Дата:** 2026-08-23
**Решение:** гистограммный бустинг вместо `GradientBoostingClassifier`.
**Причина:** на 26 тысячах строк он на порядок быстрее при том же качестве и
штатно работает с пропусками. Это позволило подобрать гиперпараметры на всех
четырёх уровнях ablation вместо переноса настроек с одного уровня.
**Последствия:** ни одна модель не использует `class_weight`, SMOTE или
oversampling — вероятности не смещены (раздел 10.3).

### D-018. Модуль `reporting.py` и скрипт `make_report.py` добавлены сверх спецификации

**Дата:** 2026-08-23
**Решение:** генерация markdown-отчётов вынесена в `src/xg_context/reporting.py`,
а построение графиков и анализ ошибок — в `scripts/make_report.py`.
**Причина:** `run_experiments.py` обучает лестницу около двадцати минут;
смешивать это с оформлением отчёта означало бы переобучать модели ради
исправления подписи на графике. `make_report.py` читает сохранённые таблицы
и предсказания и выполняется за секунды.
**Последствия:** к четырём командам спецификации добавляется пятая; она
описана в README и в `PROGRESS.md`.

### D-019. Формулировка про selection bias приведена в соответствие данным

**Дата:** 2026-08-23
**Решение:** в отчёте больше не утверждается, что «selection bias отсутствует».
**Причина:** на полной выборке из 37 488 ударов защитного контекста лишён
ровно один. Сравнивать распределения групп при n = 1 статистически бессмысленно.
Честная формулировка — не «смещение проверено и не найдено», а «смещение
невозможно при таком объёме потерь».
**Последствия:** текст вывода выбирается кодом по фактическому числу
исключённых строк (`_selection_bias_verdict`), а не задан заранее.

## Результаты, зафиксированные по данным

- **Главный результат.** Собственный защитный контекст улучшает log loss на
  0.0119 (логистическая регрессия) и 0.0107 (случайный лес); 95% доверительные
  интервалы парного bootstrap по матчам целиком лежат ниже нуля. Гипотеза H3
  подтверждена как утверждение о качестве прогноза, а не о причинности.
- **Готовые флаги StatsBomb** дают −0.0017 log loss с интервалом
  [−0.0035; +0.0002], включающим ноль: измеримой ценности сверх характеристик
  удара они не добавляют.
- **`statsbomb_xg`** остаётся немного точнее (0.2404 против 0.2427 log loss),
  но по log loss различие статистически неубедительно; по Brier score StatsBomb
  устойчиво точнее.
- **Нелинейность почти не помогает:** логистическая регрессия с защитным
  контекстом не уступает случайному лесу. Основную информацию несут признаки,
  а не форма модели. Гипотеза H4 на этих данных не подтвердилась.

## Этап 6 — Методологическое ревью и упаковка

### D-020. Sensitivity test для `n_opponents_visible`

**Дата:** 2026-08-24
**Решение:** финальная context-модель обучена дважды — с признаком
`n_opponents_visible` и без него, на тех же строках, том же разбиении и той же
процедуре подбора. Результат вынесен в отдельный раздел отчёта.
**Причина:** признак неоднозначен по смыслу. Он кодирует одновременно плотность
обороны вокруг момента и **границы поля зрения камеры**, задавшие кадр. Если бы
главный эффект держался на нём, прирост можно было бы объяснить особенностями
съёмки, а не игрой, и вывод исследования пришлось бы пересматривать.
**Результат:** эффект сохраняется. Без признака прирост составляет
−0.01141 log loss [−0.01553; −0.00736] у логистической регрессии и
−0.01034 [−0.01489; −0.00620] у случайного леса — оба интервала целиком ниже нуля.
Собственный вклад самого признака мал: −0.00044 log loss с интервалом
[−0.00091; +0.00002], включающим ноль. По Brier score вклад формально устойчив
(−0.00019 [−0.00034; −0.00004]), но составляет около 4% общего эффекта.
**Последствия:** главный вывод устойчив к этому конфаундеру. Признак остаётся
в модели, но в отчётах явно сказано, что интерпретировать его как «плотность
обороны» нельзя.

### D-021. Формулировки приведены к строгости, требуемой данными

**Дата:** 2026-08-24
**Решение:** три формулировки исправлены и закреплены в коде генератора отчёта.
**Причина и содержание:**

1. **Флаги StatsBomb.** Раньше писалось, что отсутствие прироста от готовых
   флагов «делает эффект принадлежащим именно нашей геометрии». Это неверно:
   отсутствие обнаружимого эффекта у одной группы признаков не доказывает
   исключительность вклада другой — это два отдельных сравнения, а не тест на
   исключительность. Корректная формулировка: *готовые флаги не дали
   обнаружимого дополнительного улучшения, тогда как самостоятельно
   рассчитанные пространственные признаки дали устойчивый прирост*.
2. **Сравнение со StatsBomb.** Раньше писалось «модели сопоставимы» и
   «неразличимы». Теперь: *статистически устойчивого различия по log loss
   не обнаружено*, с явным указанием, что по Brier score `statsbomb_xg`
   устойчиво лучше. Отсутствие обнаружимого различия не равно равенству моделей.
3. **Пример с `one_on_one`.** Снижение прогноза 0.526 → 0.097 подавалось как
   успех защитного контекста. При `statsbomb_xg ≈ 0.0002` это неверно: обе наши
   модели ошибаются на два порядка. Пример переписан как **failure case**
   аддитивной линейной модели, в которой бинарный флаг не может быть отменён
   геометрией.

**Последствия:** формулировки о значимости выбираются кодом по фактическим
интервалам; правила зафиксированы в docstring `xg_context.reporting`.

### D-022. Лиги сравниваются по относительному качеству, а не по сырому log loss

**Дата:** 2026-08-24
**Решение:** для каждой лиги дополнительно считаются log loss и Brier
`DummyClassifier` на тех же строках, доля снятого log loss и Brier Skill Score.
Основной вывод строится на BSS.
**Причина:** сырой log loss механически ниже там, где реже забивают. Serie A
получала лучший сырой log loss (0.2155) просто из-за низкой доли голов (8.48%),
и трактовать это как лучшую применимость модели было ошибкой.
**Результат:** по BSS порядок другой — Serie A 0.2189, La Liga 0.1913,
Premier League 0.1887, Ligue 1 0.1775; размах 0.041. Разброс мал, значит модель
работает в четырёх лигах сопоставимо и объединение в одну популяцию оправдано.
Защитный контекст помогает во всех четырёх лигах, но в Ligue 1 слабее (+0.009 BSS
против +0.046…+0.048 в Serie A и La Liga).

### D-023. Аудит экспериментальной изоляции автоматизирован

**Дата:** 2026-08-24
**Решение:** двенадцать проверок изоляции вычисляются из фактических объектов
эксперимента при каждом запуске `run_experiments.py` и попадают в отчёт.
**Причина:** декларация «test не использовался для выбора» в тексте отчёта
ничего не гарантирует. Проверяемое утверждение гарантирует.
**Проверяется:** непересечение матчей и ударов между частями; фиксация тестовых
`shot_id` на диске; выбор модели по validation; подбор гиперпараметров только
внутри train; препроцессинг внутри `Pipeline`; одинаковые строки во всех
ablation-моделях; отсутствие `statsbomb_xg`, идентичности игрока/команды/лиги,
исхода и траектории в признаках; отсутствие перевзвешивания классов;
отсутствие пост-калибровки на test.
**Результат:** все двенадцать проверок пройдены.

## Сознательно исключено из версии 1.0

Это **не** технический долг: перечисленное намеренно оставлено за рамками
релиза 1.0 и остаётся возможным направлением развития.

- **Leave-one-league-out.** Решением владельца (пункт 8) допустима только как
  необязательная проверка после завершения основного исследования. Переносимость
  между лигами уже оценена относительным качеством внутри каждой лиги (D-022),
  чего для заявленного исследовательского вопроса достаточно.
- **PCA на пространственных признаках.** Спецификация (раздел 11) прямо
  предостерегает от включения PCA ради упоминания метода. Защитных признаков
  четырнадцать, интерпретируемость важнее компактности, а логистическая регрессия
  на них не переобучается — практической нужды в снижении размерности нет.
- **Нейросеть, приложение, признаки StatsBomb 360.** Исключены прямым указанием
  владельца проекта. Для 360 есть и содержательная причина: ни один из 1517
  матчей выборки не имеет файла 360 (D-010).
